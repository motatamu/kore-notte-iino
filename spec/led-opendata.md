# バス行先表示（LED）オープンデータ形式 v0.1（提案）

**ひとことで**：バスの前面・側面の行先表示器（LED）に出ている内容を、GTFS の系統・行先に紐づけた CSV 2 枚で公開するための形式です。
事業者はすでに表示器用の「コマ表」（系統番号・経由・行先・英字…）を持っているはずなので、**それを GTFS のキーと並べて CSV にするだけ**を想定しています。新しいデータを作ってもらう提案ではありません。

- 置き場所は問いません。オープンデータカタログに単独の CSV として登録しても、GTFS-JP の zip に同梱しても同じです（zip 同梱は任意）。
- 文字コードは UTF-8（BOM 可）、1 行目は列名、区切りはカンマ。GTFS のファイルと同じ流儀です。
- ライセンスは GTFS と同じ CC BY 4.0 を想定しています。
- 実装例：[これ乗っていいの？](https://motatamu.github.io/kore-notte-iino/)（`led_front.txt` / `led_side.txt` を読み、ドット表示を実車どおりに描きます）

## なぜ必要か

GTFS には `trip_headsign`（行先の文字）と `route_color`（系統色）はありますが、実車の表示器が **どの経由地を・どの段に・どの大きさで** 出しているかは入っていません。実際の名古屋市営バスでは、同じ「上社」行きでも系統によって経由を出す／出さない、上段に小さく出す／行先の左に 2 段で出す、まわり表示を矢印で出す／文字で出す／出さない、と表示の流儀が系統×行先ごとに違います。
乗る側のアプリが「目の前のバスの表示と同じ絵」を見せるには、この情報が要ります。現状は実車を撮影して 1 件ずつ判読するしかなく、本アプリでも 150 件ほどを人手で登録しました。この形式はその人手作業を **事業者の手元にある表 1 枚** に置き換えるものです。

## ファイル

| ファイル | 内容 | 必須 |
|---|---|---|
| `led_front.txt` | 前面（正面）の行先表示 | ○ |
| `led_side.txt` | 側面の行先表示（上段ヘッダー＋停留所名の柱） | 任意 |

## GTFS との紐付け（共通）

| 列 | 内容 |
|---|---|
| `route_id` | GTFS `routes.txt` の `route_id`。**あれば必ずこれで照合**します |
| `route_short_name` | 系統名（`routes.txt` の `route_short_name`。無い事業者は `route_long_name`）。人が読むため、および `route_id` が無いときの照合用 |
| `trip_headsign` | `trips.txt` の `trip_headsign`（停留所ごとに行先が変わる便は `stop_times.txt` の `stop_headsign`）と **文字どおり一致** させてください。`*` と書くとその系統の全行先に適用 |
| `board_stop_name` | 乗車する停留所によって表示が変わる便（周回バスの区間表示など）だけ、停留所名を入れます。通常は空 |
| `source` | 典拠・メモ（任意・自由記述。撮影日や車両番号など）。アプリには使われません |

照合の規則：`route_id` があれば `route_id`＋`trip_headsign`、無ければ `route_short_name`＋`trip_headsign` の完全一致。異体字セレクタ（「辻󠄀」の U+E0100 など）は無視して照合します。GTFS に無い系統・行先の行は無視されます（ダイヤ改正で消えた行先が残っていても害はありません）。

## led_front.txt（前面）

| 列 | 値 | 内容 |
|---|---|---|
| `route_box` | 空 / `none` | 系統番号の枠。空＝系統名から標準の枠を描く（例：「栄15」1 行枠、「基幹2」上下 2 段枠、「幹名駅2」階段状）。`none`＝系統を表示しない（出入庫系統など、行先のみ光る便） |
| `via_mode` | 空 / `none` / `inline` / `top` / `stack` | 経由地の出し方。空＝GTFS の行先に書かれた経由を行先の左に小さく 1 行で出す（「赤塚・安井町西」）。`none`＝経由を出さない。`inline`＝`via_text` を行先の左に 1 行で出す。`top`＝`via_text` を上段に小さく、行先を下段に大きく出す（2 段）。`stack`＝`via_text` を行先の左に 2 段縦積みで出す（「西部医療／センター」） |
| `via_text` | 文字列 | `via_mode` が `inline`/`top`/`stack` のときの経由の文字。`stack` は行を「/」で区切る（最大 4 行）。末尾に「・」を付けると中黒を出す（`stack` では 2 段ブロックの右・縦中央に 1 個） |
| `dest_text` | 文字列 | 行先の表示文字が GTFS の行先と違うときだけ書く（例：GTFS「吹上」→ 実車「吹上（振興会館）」。括弧部分は小さい字で描かれます） |
| `dest_romaji` | 文字列 | 行先のローマ字（例「Nan-yo Kotsu Hiroba」）。空＝GTFS の `translations.txt` 等から引く |
| `loop_style` | 空 / `none` / `text` / `badge` | 「左まわり／右まわり」の出し方（行先に「◯まわり」を含む便のみ）。空＝系統枠の下に回転矢印＋文字。`none`＝まわり表示なし。`text`＝上段に文字だけ（矢印なし）。`badge`＝巡回系統でも 1 行枠＋枠下に矢印 |
| `note_text` | 文字列 | ローマ字の下にもう 1 段出す注記（例「（運転免許試験場）」） |
| `verified` | 空 / `1` / `0` | 実車の表示と一致していることを確認済みか。事業者が公開するデータでは常に `1`（省略可）。第三者が収集したデータで、表示は登録したが実車未確認なら `0`（アプリは表示を適用しつつ「自動生成」の注記を出す） |

## led_side.txt（側面）

側面は「上段ヘッダー（系統名＋行先ローマ字）」と「停留所名の柱（進行方向順・右端が始発側）」で構成されます。柱に出す停留所は GTFS の停車順から機械的には決められない（通過済みでも残る、主要停留所だけが選ばれる）ため、実車どおりの並びを書きます。

| 列 | 内容 |
|---|---|
| `origin_stop_name` | 始発停留所によって柱が変わる便だけ、始発停留所名。通常は空 |
| `stop_name_1` 〜 `stop_name_6` | 柱に出す停留所名を進行方向順に左から詰める（4 本が標準）。1 本の柱の中で 2 段に折り返す名前は「/」で区切る（「東部医療/センター」） |
| `header_style` | 空 / `route_only`。空＝「系統名＋行先ローマ字」。`route_only`＝系統名のみ（例「南陽　巡回」） |
| `header_loop` | 空 / `1`。`1`＝ヘッダーに回転矢印＋「◯まわり」を出す |
| `header_romaji` | ヘッダーのローマ字を 2 行に折り返すとき「/」で区切って書く（「Nagoya Eki/(Nagoya Sta.)」）。空＝1 行 |

柱が無くヘッダーだけ分かっている場合は `stop_name_*` を空のままにできます（アプリは側面表示を出さず、ヘッダーの折返し情報だけ使います）。

（`source` 以外は `led_side.txt` の実データと同じ行です）

## v0.1 で扱わないもの

- 事業者固有の専用デザイン（なごや観光ルートバス「メーグル」の 3 段表示、都心ループ C-758 の区間表示、SRT の白バッジ＋ピクトグラム）。本アプリではこれらは個別実装のままです。表現したい事業者が増えたら列を足します
- LED の発光色（アンバー／白）、フォント、ドットピッチ。描き方はアプリ側の責任にしています
- 停留所別に切り替わる前面表示（`board_stop_name` 列は予約済みですが、本アプリ v0.1 の読み込みでは無視します）

## 事業者の方へ：何を出せばよいか

表示器メーカーの編集ソフトにある「コマ」の一覧（コマ番号・系統・上段・下段・経由・英字・まわり）を書き出し、そのコマが使われる便の `route_id` と `trip_headsign` を横に並べたものが、ほぼそのままこの CSV になります。既存の表を組み合わせるだけで、新しい調査や撮影は要りません。1 枚できれば、この形式を読むアプリ全部で、その日から実車どおりの表示が出ます。
